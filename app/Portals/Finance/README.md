## 账户及余额

- 财务工作台打开后每小时自动刷新已连接、已启用且配置完整的 PayPal 账户，先余额后增量交易；连接异常及停用账户跳过。刷新失败显示连接异常，手动刷新成功恢复已连接后才重新纳入自动更新。复用手动刷新的状态提示与防重复提交，浏览器休眠后回到页面会检查并补做已到期的刷新。关闭页面后不执行，不依赖 Windows 任务计划或 Laravel 调度器。

- PayPal/信用卡共用新增、编辑表单，保存名称（唯一）、类型、主币种、状态和备注，生成内部唯一账户标识。编辑回填已存资料；未保存连接配置时明确提示，已有快照不代表接口配置已存在。
- PayPal 保存 HTTPS 固定中转地址、SHA-1 指纹、HMAC Key ID、加密 HMAC 密钥和服务器备注。密钥填写 VPS 配置中的 Base64 文本，严格解码后至少 32 字节；签名使用解码后的字节。密钥不进入模型序列化、表单回填或校验失败的旧输入；留空保留原值，填写新值则重置。ERP 不保存 PayPal Client ID/Client Secret。
- 财务独立维护 `finance_payment_accounts`，卡片仅来自已保存的财务账户，不再读取物流账户、物流余额。默认账户不再由迁移生成，也不从物流账户生成；用户在财务系统添加账户并配置接口。旧 `legacy_card_key` 字段和展示资料表保留存量数据，但不再参与账户读取、绑定、校验或保存；现有财务账户统一使用 `finance-<id>`，保留账户 ID、连接资料和活动名称。
- 删除仍需财务管理权限及弹窗二次确认，有历史交易也允许删除。账户采用软删除；同一事务中永久清理该账户的财务交易、结算补充、人工余额、余额快照、同步原始响应和日志，并从已结账报表快照中移除该账户行，保留其他账户及月份锁。只操作财务专用表，不删除物流或其他系统的原始数据。
- `2026_11_04_000005` 将账户名称唯一约束改为只约束未删除账户（含停用账户）。已删除账户保留原名称和历史记录，名称可重新用于新增或改名。表单校验与数据库唯一索引保持一致；`active_account_name` 为自动生成的内部字段，不回显、不允许表单写入。
- 信用卡仅维护通用资料，不提供 PayPal 配置、自动刷新或交易 API；原有人工余额功能按用户此前要求保留。
- PayPal 单账户手动刷新调用 `balances`。单账户及刷新全部均在对应卡片内显示等待、刷新中、成功或失败信息，余额、余额时间和顶部合计直接更新，无需整页刷新或点击查看最新余额。刷新全部逐账户顺序请求，一个失败后继续其他账户；失败保留最近成功快照。完成后按已连接、已关闭、连接异常、未连接排序，同状态保留账户顺序。
- 保存成功等页面顶部通知显示 10 秒后自动移除；余额刷新提示留在对应卡片内，表单校验错误保留供修改。
- 卡片右上角刷新余额，未配置或停用时禁用；底部统一为编辑、活动、删除。点击活动直接进入 PayPal 订单列表，自动筛选当前账户；在列表调整日期、交易范围、自定义条件后导出筛选结果，或勾选账户、记录导出。工作台不再加载旧活动报告及余额变动弹窗。状态基于最近一次已完成的余额刷新：成功为“已连接”，首次或再次刷新失败均显示“连接异常”；尚未尝试连接时显示“未连接”，错误提示显示在卡片内。停用优先显示“已关闭”。状态不表示后台持续探测，事务同步的业务失败不改变余额连接状态。
- 余额只读取 `finance_balance_snapshots` 中该财务账户最新时间点的整份 VPS 响应，币种消失时不沿用旧币种。保留接口 `total_balance`，缺失字段显示不可用，不按账户名称推断零余额。没有财务快照时显示暂无余额，不回退到物流数据；刷新失败保留最近成功的财务快照。停用账户不计入合计，已有财务快照或交易后类型不可改变。
- 交易同步、原始响应、分类、报表和导出使用财务表。支付账户筛选来自财务账户和已保存的财务记录，不预置物流账户名称。本次数据来源隔离复用已有财务专用表，无需重建表，不复制或删除物流业务数据。
- 工作台币种下拉只列出最新财务余额快照实际包含的币种（含停用账户的历史快照），按原币金额分类展示与汇总，不进行显示汇率折算。合计仅包含启用账户的所选币种；没有该币种的卡片保留并显示空值，缺失金额不按零处理。移除首页“编辑汇率”入口及弹窗，旧显示汇率配置不再影响 PayPal 余额；配置中心的会计月汇率及月度人民币报表保持独立。

## 中转安全与真实联调

实现位于 `FinanceRelayClient`、`FinancePayPalSyncService`。只允许 `balances`、`transaction_search` 和固定查询参数，禁止自由 URL 转发、重定向及支付写操作。TLS 在发送 HTTP 前校验账户证书 SHA-1 指纹、证书身份和 TLS 版本；请求 HMAC 与响应 HMAC 均必须通过。

若 PHP 的默认 CA 文件不可用，设置 `FINANCE_RELAY_CA_BUNDLE` 为本机可信 PEM 证书包路径。本地已设置为 Git 附带的 CA 包；其他环境需要自己的有效路径。禁止以关闭验证代替配置 CA。

用户后续提供的 `paypal_relay_balance.py` 明确了现有客户端协议。系统已对应其 Base64 解码、32 位十六进制 nonce、固定 TLS 1.2，以及“HTTP 状态码、响应时间戳、请求 nonce、正文 SHA-256”顺序的响应签名，见 [relay-protocol.md](relay-protocol.md)。实际地址、指纹和密钥只维护在账户配置中，不复制到版本库。

2026-11-04 按用户授权将所提供脚本的连接资料对应到现有账户，并分别执行原 Python 客户端和 ERP 余额请求。原客户端报 `SSLEOFError`，VPS 在返回证书前断开 TLS 握手；尚未获得经过验签的新余额，不将本地测试通过视为真实 VPS 联通。失败保留原快照。已有物流数据来自 `/api/paypal/import` 的已签名上传接收流程。该旧上传协议继续保留，不能将它的全局接收密钥直接复制成各账户中转密钥。

同日后续复测，VPS 已能完成 TLS 1.2 握手且指纹匹配，但原客户端协议请求返回 HTTP 403，正文错误为 `forbidden`，未带响应签名头。客户端不能据此确定拒绝原因，需要对应的 VPS 日志。系统对此显示拒绝访问及检查项，不再误报签名过期；未验签的正文不保存为业务数据。

## 交易、原始数据及导出

- 选择账户、开始/结束日期和时区后手动同步 `transaction_search`，按 UTC 存储。时间范围分成最多 7 天的小段，逐段翻页，校验页码、总页数、总条数和响应大小，并设置请求超时与同步页数上限。
- 按需求示例对应的 PayPal 默认口径同步余额影响记录，显式传 `balance_affecting_records_only=Y`，金额方向转换为原有活动报告所用的 Credit/Debit 标记，不冒用不存在的响应字段。未影响余额的记录不由此请求拉取。字段核对来源为 [PayPal 官方接口定义](https://developer.paypal.com/api/transaction-search/v1/schema.json)。
- 每页通过签名和业务字段校验后以数据库事务保存。以支付账户 ID + 交易号 + 事件代码唯一去重，重复同步更新既有记录。失败页不保存；此前已验证页保留，日志标记失败及已保存数量，可重试补齐。
- `finance_payment_transactions.raw_payload` 留存每笔原始 JSON；`finance_sync_pages.raw_response` 留存验签成功的整页原始响应；列表提供原始 JSON 查看，受财务门户及订单菜单权限检查。
- 接口交易投影到 `finance_records`，复用订单列表、条件查询、时区、CSV/TSV/Excel 导出和原有活动报告；新增“导出当前筛选结果”。同步表单可勾选同步后导出余额变动 Excel。
- 活动报告的交易类型读取配置中心“PayPal类型分类”的交易分类，合并重复分类，支持全部类型和待分类；筛选和报告分类列使用最新原始类型映射。日期范围仅提供自定义开始、结束日期；格式仅提供真实 XLS、XLSX，XLS 超过65535条交易时提示改用 XLSX 或缩小日期范围。
- 订单列表及常规导出使用接口交易已应用的会计分类、方向、月汇率和人民币金额，锁定后不动态套用新会计分类。活动报告的类型分类筛选不修改会计交易或已锁定月报。原有表格记录继续使用原精确分类机制。ERP 销售订单关联规则尚需按方案 §8 确认，未伪造自动关联。
- 订单数据禁用文件导入；原有支付明细和分类仍支持模板、批量导入和导出。域名人员分组仅供查看，直接读取“域名与店铺信息管理”的域名、使用人（user_name）及团队，不提供新增、编辑、导入、导出或模板接口；报表使用同一来源。原币数据与原始 JSON 保留，不执行导入文件公式。
- 信用卡订单页直接查询物流订单，沿用物流统计的 `CreditCardBy` 标签识别规则，不复制到财务订单表。账户选项、条件筛选、日期时区、分页及勾选导出均读取该来源；原币信息取 Shopify 原始数据，美元金额取物流的 paid_amount_usd。页面不再展示物流未提供的商户号、卡号或 3D 信息。
- PayPal 账户、余额和交易独立维护：余额只读取财务中转接口保存的 `finance_balance_snapshots`；交易通过财务接口同步，不再自动复制物流 PayPal 交易。旧系统关联字段仅保留兼容，不参与余额读取或自动同步。

## 分类、月汇率和报表

配置中心的“会计设置”支持：

1. 原始事件代码、交易标题或说明作为来源，等于/包含/前缀匹配；维护规则名称、分类、方向、损耗科目、优先级和启停状态，优先级相同时按 ID 匹配第一条。
2. 按会计月份（北京时间）维护原币→CNY 固定汇率、来源、更新人和时间；CNY 固定为 1，缺少汇率显示“待配置”。保存汇率会重算该未锁定月的接口交易。
3. 对选定未锁定月份重新应用分类和汇率。结账只允许已结束月份，有未分类或缺失汇率时阻止结账。
4. 结账冻结账户/分类/方向/金额/人民币金额的报表快照。月份行锁串行化同步、重分类、汇率更新和结账；锁定后拒绝该月的新同步、汇率修改及重分类。不开放解锁或锁定后补录，避免在方案 §8 未明确前改变历史。

报表提供账户→支付大类→损耗科目三级汇总，支持月份、账户、大类、币种及是否包含未分类筛选，导出 Excel。原币金额、接口带符号手续费及其净额分开展示；缺少手续费时不按 0 计算，缺少汇率时不输出部分人民币合计。

最终净损耗公式、各财务分类的正式损耗归属、ERP 订单关联、解锁与补录审批仍需按方案 §8 确认，不擅自给出财务口径。`balance_net_summary`、`daily_summary` 为可选增强，尚未启用。信用卡接口仍按一期范围禁用。

## 环境数据边界（2026-11-05）

首次部署只初始化表结构、菜单权限和通用交易类型字典；不写入开发工作簿中的域名人员归属、历史月汇率或固定名称账户。`000004`、`000016` 迁移保留历史文件名但不再写入业务数据。`000015` 只保留旧字段的结构兼容，不创建或绑定账户。PayPal 余额及交易只使用财务接口来源；信用卡订单的原有共享数据来源保留。其他财务账户、人工余额、报表补充数据、会计规则和汇率需要在当前环境维护。

变更不会删除已存在的业务记录，也不会重跑已执行的迁移。已上线环境需先备份、核对迁移记录与业务记录来源，再按确认的清单清理误初始化资料；不能按账户名称或日期直接删除。不要导入开发数据库或执行 `migrate:fresh` 处理线上数据。当前仓库检查未发现数据库导出/上传部署脚本，是否曾导入整库需另查实际发布流程和数据库操作记录。

### 接口交易的业务订单关联与线上核查

PayPal 订单详情、结算及物流字段筛选通过接口交易号或账单号匹配业务订单的交易号、网关订单号、账单号或支付参考号，不依赖旧 PayPal 账户绑定；匹配多个业务订单时不自动关联。此关联只读取业务订单补充信息，不复制其他系统的 PayPal 余额或交易。

上线先备份数据库并发布代码，再执行 `php artisan finance:audit-data`。该命令只读列出财务表数量、账户配置状态、旧关联、交易数量和月汇率，不输出密钥、不删除记录。根据核查输出及线上同步/人工维护记录确认清理清单；已结账数据与来源不明确的交易不能自动清理。


### 余额优先刷新与后台订单队列

工作台刷新只等待余额接口；成功后将订单同步放入独立 database 连接 finance_orders、队列 finance-orders，不依赖默认 QUEUE_CONNECTION，默认配置为 sync 时也不会在页面请求内同步订单。订单成功或失败仍记录在 finance_sync_logs，同账户任务通过唯一锁避免重复排队，停用或删除后未执行的任务直接跳过。

使用项目现有 Laravel 调度器（每分钟运行 php artisan schedule:run），新增调度项会串行处理 finance-orders 队列。队列表使用现有 jobs 表，不新增业务数据迁移。发布后如缓存配置需刷新配置缓存，并确认调度器正常运行；未启动调度器时余额可立即更新，但订单将留在队列等待。也可用独立常驻 worker：php artisan queue:work finance_orders --queue=finance-orders --tries=1 --timeout=900。该连接 retry_after=960，大于任务超时。

订单列表刷新弹窗按账户展示排队、同步中、成功、失败或跳过，并每2秒轮询处理条数和失败原因。状态保存在应用缓存中24小时；生产环境需使用持久共享缓存（database、redis或单机file，不能使用array/null），Web和队列进程必须使用同一缓存配置。重复提交通过账户级原子锁沿用活动任务，后台失败保留已处理条数，状态接口按发起人和财务菜单权限检查访问。

首次历史回补默认回推6个月，可通过 config/finance.php 的 relay.initial_months 调整；先按会计月份拆分，再按最多7天一段请求，每段依据接口 total_pages 逐页读取，不能把不足500条视作最后一页。接口实际每页仅100条时仍取完所有页，并校验累计条数等于 total_items，完成后才记录该月份成功进度。后续正常增量获取近5小时；已锁定月份保留现有快照并跳过。

历史完整性：时间段从上一段结束后1秒续接，按实际范围截断末段，天数可以不同。未被成功区间完整覆盖的失败或中断范围会优先回补，不会因较新日期同步成功而越过历史缺口。同段跨页重复交易会触发重试或失败，不会仅凭累计行数将重复页判定为完整；失败不会标记为完成。

每小时自动订单获取：finance:paypal-orders:enqueue 由调度器每小时运行，为启用且已配置接口的账户排队；独立订单worker按顺序消费。首次回补6个月，后续通常查询当前时间前5小时；若最近成功进度早于该窗口，则从成功进度补齐停机间隔，并优先修复未完成范围。同一账户以 transaction_id + transaction_event_code 组合更新或插入，finance_records 使用对应指纹；相同交易号的不同事件不能误合并。此规则不跨财务账户自动合并。

订单刷新进度恢复及追加：账户选择支持多选、全选，运行中仍可追加其他账户；同一账户沿用未完成任务。批次按发起用户保存在共享缓存，单账户/全部余额刷新也加入该用户同一批次；返回订单页后通过latest接口恢复每账户状态、处理数和失败原因。页面切换不会取消后台任务。结果保留24小时；同账户完成后再次提交会替换该账户上一轮状态，其他账户结果保留。

已有账户历史补齐：每次订单同步都会合并成功时间区间，检查当前时间回推6个月的连续覆盖，不能仅凭最近一次成功记录进入增量。存在缺口时先从最早缺失时间补到当前，完整后才按近5小时正常增量。锁定月份存在未确认缺口时明确报告历史未完成，不自动解锁或显示回补成功。订单导出按钮在生成/下载期间显示转圈并阻止重复提交，出错后恢复按钮。
